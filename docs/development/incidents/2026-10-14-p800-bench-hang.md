# Incident: intermittent XPU kernel hang during the phase-3 bench (2026-10-14)

**Status:** mitigated (watchdog + PID-kill recovery), root cause **not** identified.
**Severity:** device hang — requires `kill -9` of the offending process; device
recovers without reset (card 6, healthy OAM).

Raw trace artifacts for this incident live in
[`results/p800/diagnostics/2026-10-14/`](../../results/p800/diagnostics/2026-10-14/).

## What happened

During the first full `scripts/bench.py --sizes <18 sizes> --trials 50` run of
the section-7 matrix, the process blocked **forever** in the per-trial
`torch.cuda.synchronize()` of the interleaved timing loop while one queued
kernel never completed:

```text
Thread 18540 (active): "MainThread"
    synchronize (torch/cuda/__init__.py:1083)
    main (bench.py:330)
    <module> (bench.py:754)
```

(`bench.py:330` is the sync after `ev_end.record()`; the launch itself had
returned — the hang is device-side.) Snapshot during the hang
([hung-process-pyspy.txt](../../results/p800/diagnostics/2026-10-14/hung-process-pyspy.txt)):

```text
xpu-smi -i 6:  49C  141W/400W  1694MiB/98304MiB  XPU-Util 100%   (unchanged for 30+ min)
```

`py-spy dump` re-sampled at ~19:25, 19:27, 19:28 (local) showed the identical
frames every time — a hard hang, not a slow kernel. The last size with a fully
printed row was `N=8192`; 4 vendor `ASSERT-FAIL` pairs on stderr (expected above
`N=2048`, see [vendor-assert-stderr.txt](../../results/p800/diagnostics/2026-10-14/vendor-assert-stderr.txt))
place the hang somewhere in the `N=32768..524288` window (stdout was
block-buffered, so exact size attribution is not reliable for that run).

## Recovery (worked)

```bash
kill -9 <pid>          # by exact PID — never pkill -f (see device-stack.md)
# within seconds: xpu-smi shows 0% util, 0 MiB; next kernel launches fine
```

No device reset was needed. Card 6 stayed healthy for the remaining ~4 h of
matrix + block runs.

## Isolation results (hang not reproduced)

| Probe | Result |
|---|---|
| all candidate kernels at `N=16384` (incl. M4 `b=64` both variants) | all OK |
| full bench `--sizes 32768 --trials 50` (correctness + timing + vendor) | completed, exit 0 |
| full bench `--sizes 65536 --trials 50` | completed, exit 0 ([log](../../results/p800/diagnostics/2026-10-14/bench65536-isolated.log)) |
| 65-round interleaved event-loop mimic at `N=32768` (warmup+trials, shuffled) | 65/65 rounds, `ALL DONE` ([log](../../results/p800/diagnostics/2026-10-14/bisect32768-65rounds.log)) |
| retry of the full 18-size run (`python -u`, new process) | completed cleanly; all published data comes from this run |

The second full-run attempt was killed by a **watchdog false positive** (see
below), not by the hang; the third attempt completed. Net: one genuine hang in
~5 full-process-hours on the same GPU, zero reproductions in isolation.

## Related false positive: "stall" vs slow batch phases

A watchdog that kills on log silence **will** kill healthy runs at
`N >= 2^19`: the per-size stdout line only prints when a size finishes, and the
`B=64` timing phase is legitimately silent for tens of minutes. Measured
([bench65536-isolated.log](../../results/p800/diagnostics/2026-10-14/bench65536-isolated.log)):

```text
b=64 api_ms:  247 ms @ N=2^15   538 ms @ N=2^16
```

Linear extrapolation: ~4.3 s/call at `N=2^19`, ~8.7 s/call at `N=2^20`; with
16 batch entries x 60 calls (50 trials + 10 warmup) the batch phase alone is
~30 min at `2^19` and ~60 min at `2^20`. The first watchdog (12-min threshold)
killed a healthy run mid-`2^19`
([watchdog-timeline.txt](../../results/p800/diagnostics/2026-10-14/watchdog-timeline.txt)).
**Rule: stall thresholds for this bench must exceed ~2 h, or progress must be
instrumented per candidate.** A genuine hang and a busy-silent phase are
indistinguishable from log mtime + `XPU-Util 100%` alone (both show 100%).

## Diagnostic notes for the next occurrence

* `py-spy dump --pid <pid>` attaches cleanly **when the GIL is released**
  (e.g. blocked in `synchronize()` — the hang signature above). On a process
  spinning in native code it fails with `Failed to find python version from
  target process`; that failure is not itself a hang signal.
* Use `scripts/diag_snapshot.sh <pid> <log>` to capture `xpu-smi`, process
  state, a `py-spy` dump and the log tail in one shot.
* The hang is **device-side** (host is parked in sync; the launch returned).
  Candidate suspects for a follow-up investigation: the XPU scheduler under
  high launch counts (the full run performs ~10^5 launches/size), or a rare
  bad launch shape — neither confirmed. It did **not** recur under the same
  candidate set, size, and protocol in isolation.

## Why this matters for the results

The published phase-3 matrix (see [results.md](../../../results.md)) comes from
the retry that completed end-to-end; its worst error is 1.1e-5 and every
candidate checked out in isolation. The incident changes **operations**
(watchdog thresholds, recovery procedure), not the numbers.
